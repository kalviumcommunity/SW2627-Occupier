# Firebase security

## Authorization model

Firebase Authentication supplies each user's UID. The matching
`users/{uid}` Firestore document supplies the role (`admin`, `branchManager`,
`staff`, or `member`). Firestore rules prevent users from changing their own
role; only an existing administrator can change role documents. Do not add
client code that writes authorization roles.

The first administrator must be provisioned by a trusted operator in the
Firebase Console:

1. Register the intended administrator through the app so the account and
   `users/{uid}` profile both exist.
2. In Firebase Console, select project `occupier-f49d0`, open **Firestore
   Database** → **Data**, and open that user's document in `users`.
3. Change only its `role` field to the string `admin`, then save.
4. Verify the selected document ID and `uid` field match the intended
   Firebase Authentication UID. Do not make this change from the client app.

Additional admin and staff role changes must be performed by an authenticated
administrator through a future trusted admin workflow or by a trusted operator
in the Console. No Firebase service-account credentials belong in the Flutter
app.

## Rules and tests

The root `firebase.json` references `firestore.rules`; the mobile Firebase
configuration references `mobile/firestore.rules`. Keep these rule files
identical when changing authorization policy. The root configuration also
deploys `storage.rules`. Profile images are limited to authenticated uploads
of JPEG files at
`profile_photos/{uid}.jpg`; reads also require Firebase Authentication. A
download URL generated by Firebase Storage is a bearer URL, so treat it as
shareable if exposed.

Booking creation must atomically write the booking and its matching
`booking_schedules` reservation. Users can read an individual schedule to
check availability, but cannot list the schedule collection or alter existing
reservations.

Run the Firestore Emulator rules tests from the repository root:

```powershell
npm run test:rules
```

Run Flutter checks from `mobile`:

```powershell
flutter test
flutter analyze
```

After review, deploy rules manually (this does not run as part of the test
script):

```powershell
firebase deploy --only firestore:rules,storage --project occupier-f49d0
```

The existing member check-in and check-out transactions also update a desk or
room status. Current rules intentionally do not permit ordinary users to
change resource status, because the resource update cannot be safely tied to a
specific occupancy document with the current data shape. Consequently, those
member transactions require a follow-up design to bind both writes before they
can succeed under these rules; do not broaden resource writes to all signed-in
users as a workaround.
